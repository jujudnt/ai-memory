# Audit du fonctionnement AI Memory

Audit du 21 septembre 2026. Code : `c11f7c0`, version `0.4.20`.
Interface réellement ouverte pendant l'audit : `0.4.19`.

## Conclusion

Le projet a une base fonctionnelle, mais n'est pas encore suffisamment fiable ni optimisé pour une distribution sans accompagnement. Les problèmes concernent surtout la distribution du composant de fond, la migration complète des archives, la reprise des transferts et les interactions entre nettoyage et sauvegarde incrémentale.

Les constats ci-dessous décrivent l'état initial, avant correction. Le suivi de correction est séparé dans la section suivante. Aucun redémarrage, changement de compte ou nettoyage n'a été effectué sur l'installation réelle pendant l'import. Aucune nouvelle connexion à un fournisseur n'a été lancée. Les tests destructifs utilisent exclusivement des données synthétiques dans des dossiers temporaires.

### Limites restantes

- Les connexions Google, Dropbox et OneDrive n'ont pas été réautorisées avec de vrais comptes pendant cette intervention. Les tests de leurs réponses ne remplacent pas une validation de bout en bout chez le fournisseur. Le transfert iCloud déjà lancé a terminé ses 1077 objets sans intervention.
- Les fichiers sources modifiés sont encore reparcourus intégralement ; l'import incrémental au niveau du parseur, contrairement à la sauvegarde brute incrémentale, reste à développer et mesurer sur de gros fichiers.
- Les versions cloud réellement distinctes ne sont pas supprimées automatiquement. Une rétention historique bornée nécessite une politique explicite et une validation des dépendances sur plusieurs machines. Aucun effacement arbitraire des anciennes bases locales ni de l'historique distant n'a été ajouté.
- Pas de nouvel adaptateur Cursor, Claude Web, Cowork ou Design ; pas de fusion automatique de projets natifs indépendants entre machines. Pas de navigateur distant de dossiers ni de lecteur complet de conversations dans le tableau de bord ; lecture/recherche paginées disponibles dans le MCP.
- Le build local est arm64 sur Python 3.14. La matrice CI utilise Python 3.12 ; Windows, notarisation de cette nouvelle version et validation sur un second Mac restent nécessaires avant une release publique.

Les sections suivantes restent le compte rendu initial ; leurs numéros de ligne et mesures se rapportent à `c11f7c0`.

## Ce que fait réellement une synchronisation

1. Lire la liste des objets de la destination configurée.
2. Produire une révision immuable des conversations locales courantes.
3. Envoyer les objets locaux absents de cette liste.
4. Recevoir les objets distants inconnus localement, dont les archives de l'autre ordinateur.
5. Vérifier les téléchargements et indexer les conversations reçues.
6. Enregistrer les confirmations puis supprimer les originaux et révisions locaux considérés comme sauvegardés.

Ainsi, « synchroniser » signifie envoyer ET recevoir. Pendant l'audit, le Mac recevait des objets (`downloading`), avec une progression observée de 476 à plus de 480 sur 1077. Il s'agit d'objets d'archive, pas de 1077 conversations. La collecte locale était indépendamment en erreur.

## Défauts prioritaires

### P1 — Le composant signé de la release macOS ne démarre pas

**Reproduit sur l'archive exacte v0.4.20 téléchargée depuis GitHub.** Exécuter `AI Memory.app/Contents/MacOS/ai-memory-cli --help` retourne le code 255 et l'erreur `mapping process and mapped file (non-platform) have different Team IDs`.

Dans `.github/workflows/release.yml:73`, le programme autonome est construit sans identité de signature PyInstaller. La signature ultérieure signe son enveloppe, mais pas les bibliothèques déjà embarquées dans l'archive du binaire. Le serveur MCP et le nouveau watcher utilisent ce composant.

La vérification statique et la notarisation ne prouvent donc pas qu'il démarre. Déplacer l'app dans Applications ne résout pas ce défaut. Mon conseil précédent était insuffisant.

**Correction :** transmettre l'identité Developer ID à PyInstaller pendant la construction ; tester le binaire signé, le démarrage MCP et un scan isolé avant de publier. Ne pas contourner la validation des bibliothèques. [Documentation PyInstaller](https://pyinstaller.org/en/stable/feature-notes.html#macos-binary-code-signing).

### P1 — Changer de Drive ne migre pas tout l'historique

**Reproduit : ancien Drive = 4 objets, nouveau = 1.** Deux sauvegardes originales et une ancienne révision restent uniquement dans l'ancien Drive. La conversation courante arrive bien.

`desktop.py:395` appelle `pull_cloud_now()` avant le changement. Mais `sync/cloud_sync.py:125` ignore les objets déjà connus et `sync/cloud_sync.py:175` applique aussi le nettoyage en mode réception seule. Les fichiers historiques sont absents ou supprimés avant leur transfert vers la nouvelle destination.

**Correction :** créer une migration persistante, conserver les fichiers nécessaires jusqu'à leur vérification dans la nouvelle destination et suivre séparément les confirmations de chaque destination. La migration doit comparer l'inventaire complet, pas seulement le nombre de conversations visibles. L'ancien Drive reste intact dans la reproduction.

### P1 — Une interruption ne conserve pas les confirmations de réception

**Reproduit : un fichier téléchargé, puis panne simulée ; zéro confirmation persistée.** Les confirmations ne sont écrites qu'en fin de synchronisation (`sync/cloud_sync.py:174`). Le dossier temporaire est supprimé en cas d'erreur comme en cas de succès.

Au prochain essai, des fichiers déjà reçus peuvent être retéléchargés. Les dépendances des originaux sont également à reconstruire. L'envoi sait généralement éviter un objet déjà présent via l'inventaire distant, mais la réception n'a pas une véritable reprise durable.

**Correction :** enregistrer chaque objet validé ou chaque petit lot, conserver un cache partiel borné, et reprendre uniquement les éléments manquants ou invalides. Une absence locale peut aussi provenir d'un nettoyage volontaire : le registre doit distinguer ces états.

### P1 — Une panne réseau iCloud devient une demande de reconnexion

**Reproduit avec une erreur DNS synthétique.** Le message obtenu parle de connexion iCloud incomplète et de code 2FA. `sync/cloud_sync.py:194` met `requires_action=True` pour toute erreur iCloud ; `watcher/service.py:96` empêche alors les tentatives automatiques.

Le texte est aussi trompeur pour un délai dépassé ou une erreur d'intégrité, qui ne prouvent pas une expiration de session. `_friendly_rclone_error()` dans `cloud/rclone_provider.py` ramène les erreurs iCloud inconnues à une explication d'authentification.

**Correction :** distinguer réseau, limitation temporaire, quota, session expirée, 2FA et intégrité. Réessayer les erreurs transitoires avec un délai croissant ; demander une action uniquement sur une réponse d'authentification explicite.

### P1 — La reconnexion dépend de l'accès au compte déjà défaillant

**Confirmé par lecture du parcours.** `desktop.py:179` exige de récupérer l'ancienne destination avant de démarrer une nouvelle connexion. Si l'ancienne session a expiré, cette récupération échoue avant d'ouvrir l'authentification du nouveau compte. Une erreur du Drive peut donc empêcher sa propre réparation.

**Correction :** séparer réauthentification du même compte et migration vers un autre compte. Pour migrer, préparer la nouvelle autorisation sans supprimer l'ancienne, puis afficher les archives effectivement récupérables. Ne pas annoncer une migration complète si l'ancienne destination est inaccessible.

### P1 — Un sous-agent Claude peut remplacer la conversation principale

**Reproduit sur deux fichiers synthétiques.** `ClaudeAdapter.scan_sessions()` inclut les fichiers sous `subagents`, et `parse_session()` utilise leur `sessionId` comme identité (`adapters/claude.py:37`, `:61`, `:104`). Si le sous-agent partage celui du parent, les deux deviennent la même conversation. Une date plus récente du sous-agent remplace le contenu principal dans l'index.

La reproduction produit une seule conversation contenant « subagent work » au lieu du fil principal. Cela ne prouve pas qu'un fil réel précis de cet ordinateur a déjà été remplacé.

**Correction :** identifier séparément les sous-agents, conserver leur rattachement au parent, et tester l'import d'un parent avec plusieurs sous-agents. Compléter aussi l'association des `tool_result` avec les `tool_use` : les sorties ne sont actuellement pas rattachées aux appels dans l'adaptateur Claude.

## Espace et performances

### P1 — Nettoyer les originaux désactive ensuite la sauvegarde incrémentale

**Reproduit.** Après une synchronisation réussie et son nettoyage, ajouter une réponse recrée une sauvegarde de l'original entier. `archive/raw_backup.py:21` exige que la version précédente soit encore locale pour écrire un delta. Or le nettoyage vient de la supprimer.

Les originaux complets et les snapshots courants s'accumulent ainsi dans le cloud au fil des modifications. Le hash évite deux copies de bytes identiques, mais pas plusieurs copies quasi identiques d'une longue conversation. Il n'existe pas de politique régulière de rétention cloud des révisions réellement distinctes. Le nettoyage sémantique actuel ne s'exécute qu'une fois et vise seulement certains doublons.

**Correction :** garder une base incrémentale ou des blocs adressés par contenu ; définir des points de contrôle bornant les chaînes ; ajouter une rétention cloud explicite avec vérification de toutes les dépendances avant suppression.

### P2 — Réception séquentielle et chaînes coûteuses

`RcloneArchiveRemote.download()` lance un nouveau processus pour chaque fichier. `_hydrate_raw_dependencies()` peut en lancer plusieurs avant la mise à jour suivante de la progression. `read_raw()` reconstruit tout le contenu pour chaque delta, avec un coût cumulé élevé sur une longue chaîne.

Sur les originaux présents localement pendant l'audit : 502 deltas, profondeur maximale 120, 23382 parcours cumulés de parents si chaque chaîne est reconstruite séparément. Ce dernier nombre n'est pas le nombre de requêtes réseau : des dépendances sont réutilisées dans le cache du transfert.

**Correction :** télécharger les objets par lots avec concurrence bornée, réutiliser les sessions du fournisseur, afficher une activité périodique pendant les transferts et les dépendances, et valider les chaînes une seule fois dans l'ordre des dépendances. Prioriser les snapshots courants pour rendre les conversations recherchables avant l'historique brut. Actuellement, le tri lexical télécharge les `raw/` avant les `snapshots/`.

### P2 — Stockage temporaire non borné et index non compacté

Mesure intermédiaire sur le Mac, pendant le transfert. Valeurs arrondies en unités binaires, conformément au calcul actuel de l'interface qui les nomme « Mo/Go ».

| Partie | Taille approximative | Explication |
| --- | ---: | --- |
| `archive/sources` | 178 Mo | Archives normalisées ; 281 fichiers pour moins de conversations indexées, donc contient aussi des variantes |
| `archive/snapshots` | 565 Mo | Révisions historiques encore locales |
| `archive/raw` | 1,40 Go | Sauvegardes des sources originales |
| `cache/incoming` | 1,45 Go | Copies temporaires du téléchargement |
| `db/memory.sqlite` | 1,46 Go | Base courante, incluant messages, outils, contenu plein texte et index |
| `db/before-v0.2.0.sqlite` | 519 Mo | Ancienne sauvegarde de base non couverte par le nettoyage |
| `bin` | 108 Mo | Composants exécutables |

Le dossier temporaire conserve les téléchargements alors qu'ils sont aussi copiés dans `archive`. Il n'a pas de plafond et aucun contrôle préalable d'espace libre pour les réceptions. Le contrôle existant concerne uniquement les envois vers un dossier local.

SQLite avait 141632 pages libres sur 382817 pages de 4096 octets : environ 553 Mo potentiellement récupérables par une maintenance adaptée, pas un gain garanti exactement identique. Supprimer des lignes ne réduit pas spontanément le fichier. Aucune maintenance de compactage ni rétention des anciennes bases n'est prévue.

`cleanup.py:13` n'est appelé qu'à la construction de `MemoryService` : l'intervalle de six heures n'est pas un vrai déclenchement périodique dans un processus restant ouvert. Il vise certains noms de fichiers dans `cache`, pas les téléchargements du navigateur ni les anciennes bases.

**Correction :** afficher séparément courant, historique, originaux, cache, index et autres fichiers ; borner et purger progressivement le cache validé ; vérifier une réserve disque ; prévoir une maintenance SQLite hors transfert et une rétention des sauvegardes internes. Ne pas supprimer l'unique copie d'un original pour réduire un compteur.

### P2 — Les scans retraitent trop de données modifiées

Le watcher rescane les sources toutes les dix secondes, relit entièrement les fichiers modifiés, les reparcourt, recompresse toute la conversation et remplace les messages, outils et index plein texte. `last_offset` est stocké mais n'est pas utilisé pour reprendre la lecture (`service.py:92`, `db/sqlite.py:130`). Les requêtes de lecture réexécutent aussi l'initialisation du schéma.

L'API d'état recalculait ses tailles en environ 115 à 144 ms lors de deux mesures ; ce n'est pas le goulot principal observé. Toutefois, elle parcourt plusieurs fois les mêmes dossiers toutes les cinq secondes et devient plus coûteuse avec le nombre de fichiers.

**Correction :** traiter les ajouts incrémentalement lorsque le format le permet, regrouper les écritures et mettre les tailles en cache. Ajouter des mesures sur une longue conversation et une bibliothèque importante, pas uniquement de petites fixtures.

La connexion Google remplace le fichier rclone entier et sa déconnexion le supprime, contrairement à la suppression par section des autres providers (`cloud/google_drive.py:87`, `:137`). Les sessions d'autres fournisseurs éventuellement présentes ne sont donc pas préservées. Les reconnexions des providers en ligne remettent systématiquement le chemin à `AI-Memory`, au lieu de conserver le dossier choisi auparavant.

Les documentations primaires confirment les contraintes : [scope Google et client partagé](https://rclone.org/drive/), [sélection OneDrive dans rclone v1.75.1](https://github.com/rclone/rclone/blob/v1.75.1/backend/onedrive/onedrive.go), [authentification iCloud](https://rclone.org/iclouddrive/). Il faut anticiper l'expiration de la session iCloud, et non exiger une connexion supposée permanente.

## Sources, projets et MCP

- Codex et Claude Code sont collectés dans leurs répertoires locaux ; les sessions de code Claude Desktop et des extensions sont reconnues par les métadonnées. Claude Web, Cowork et Design ne sont pas couverts en général ; Cursor n'a pas d'adaptateur. Le README le mentionne désormais.
- Le collecteur VS Code cherche certains fichiers `chatSessions/*.jsonl`. Il ne rejoue pas explicitement un journal de modifications JSON ni ne couvre tous les profils, éditions et anciens formats. La couverture réelle doit être testée avec des fixtures de ces versions.
- L'installateur écrit le MCP de Codex, Claude Desktop et le `mcp.json` de VS Code. Il n'installe pas une configuration utilisateur propre à Claude Code. Configurer le MCP natif VS Code n'est donc pas une preuve qu'il est disponible dans l'extension Claude Code. Codex est déclaré toujours disponible ; la détection ne respecte pas les installations personnalisées de tous les clients.
- Les filtres `date_from` / `date_to` du MCP sont explicitement ignorés (`mcp/tools.py:25`). Reproduction : une recherche demandant uniquement 2099 renvoie une conversation de 2026. Les filtres `source="claude"` ou `source="codex"` ne regroupent pas leurs variantes VS Code/Desktop.
- `get_project_history` attend un identifiant exact, sans outil dédié pour découvrir ou résoudre un nom de projet. Pour les dossiers sans Git, l'identité dépend uniquement du dernier nom du dossier : deux dossiers distincts nommés `app` deviennent le même projet (`projects/identity.py:52`). Les projets Codex utilisent leur identifiant natif, sans mécanisme de rapprochement entre projets créés indépendamment sur deux ordinateurs.
- `get_conversation` renvoie toute une conversation, outils inclus, sans pagination. Les très longues conversations peuvent saturer la réponse MCP et le contexte du client. `sync_now` attend la fin complète du transfert, alors que la configuration client annonce 60 secondes de délai outil.

## Vérifications effectuées

- Suite existante : **93 tests Python réussis** ; test JS existant réussi. Ces résultats ne valident pas le binaire signé ni les comptes cloud réels.
- Release v0.4.20 téléchargée et décompressée dans un dossier temporaire : échec du binaire avec `--help`, code 255.
- Lecture des états, tailles et paramètres SQLite en cours d'exécution ; aucune maintenance sur la base réelle.
- Inspection réelle du tableau de bord, des réglages, des diagnostics et de l'ouverture du formulaire de changement.
- Reproductions synthétiques disponibles dans `scripts/audit_workflow.py` et `scripts/audit_desktop.cjs`.

```sh
.venv/bin/python scripts/audit_workflow.py
node scripts/audit_desktop.cjs
```

Ces scripts affichent le comportement observé. Ce ne sont pas des tests de régression qui prétendent réussir : les résultats identifient les défauts encore présents. Les tests cloud des scripts utilisent des dossiers temporaires ou des doublures, jamais les identifiants de l'utilisateur.

## Ordre de correction recommandé

1. Corriger et tester le binaire signé, puis rendre la réparation/mise à jour du watcher accessible et vérifier sa version réelle.
2. Sécuriser la migration complète, les confirmations persistantes, les erreurs transitoires et la reconnexion ; ajouter des tests interruption/reprise et multi-destinations.
3. Corriger l'identité des sous-agents Claude et vérifier la fidélité des importations par source.
4. Refaire l'équilibre entre deltas, points de contrôle, rétention cloud et cache borné ; mesurer l'espace avant/après.
5. Accélérer les transferts et la collecte, puis simplifier les états et boutons de l'interface autour des comportements corrigés.
6. Valider chaque fournisseur avec un compte réel, puis tester le parcours complet sur deux Macs et Windows avant une nouvelle release.
